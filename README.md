# @unlitcube/node-red-broute

Wi-SUN USB アダプタを使って、日本の低圧スマートメーターから **B ルート**で計測値を読む Node-RED ノードです。

- 瞬時電力・瞬時電流・積算電力量などを、そのまま使える JSON のオブジェクトでフローへ流します。
- 接続・再試行・再接続は、ノードが自動で行います。フローの側は、流れてくる値を受け取るだけです。
- 状態の確認・設定・診断ができる Web UI を同梱しています。ダッシュボードを作る必要はありません。

Reads Japanese low-voltage smart meters over the B-route with a Wi-SUN USB adapter (tested with RATOC RS-WSUHA only).
The node handles joining, retries and reconnection, and outputs plain JSON. A built-in Web UI shows status and settings.
The editor, the Web UI and this document are in Japanese only, because the B-route is a service for smart meters in Japan.
This is an unofficial package. It is not affiliated with or endorsed by RATOC Systems, ROHM, the Japanese transmission and distribution companies, the ECHONET Consortium or the Wi-SUN Alliance.

## 必要なもの

| もの | 内容 |
|---|---|
| Node-RED | 3.1 以上（3.1.3・4.0.9・4.1.2 で確かめました） |
| Node.js | 18 以上 |
| Wi-SUN USB アダプタ | 確かめたのは RATOC RS-WSUHA だけです。ほかのアダプタで動くかは確かめていません |
| B ルートの認証 ID とパスワード | 下の「B ルートの申し込み」 |

シミュレーターで試すだけなら、アダプタと認証情報は要りません。

### B ルートの申し込み

B ルートを使うには、お住まいの地域の一般送配電事業者（東京電力パワーグリッドなど）へ B ルートサービスを申し込みます。届いた認証 ID（32 桁）とパスワード（12 桁）を設定します。申し込みの窓口と開通までの日数は事業者によって違います。認証情報は人に渡さないでください。

### 使う前に知っておくこと

- アダプタは送信時間の積算を持ち、上限（ARIB STD-T108 に基づく 1 時間あたり 360 秒）に達すると送信を止めます。このノードは、つながらずに再試行を続けるときに積算を読み、上限の約 70% を超えていれば 10 分休みます。
- アダプタは、技適マークのある機器（技術基準適合証明または工事設計認証を受けた機器）を使ってください。
- 計測値は参考値で、請求の値と一致するとは限りません。
- 本ソフトウェアは無保証です（[LICENSE](LICENSE)）。

## 5 分で試す

実機も B ルートの契約も要りません。シミュレーターの例を読み込むだけで動きます。

1. Node-RED のメニューから「パレットの管理」→「ノードを追加」で `@unlitcube/node-red-broute` を入れます（`broute` か `wsuha` で探せます）。コマンドで入れるなら次のとおりです。

   ```bash
   cd ~/.node-red
   npm install @unlitcube/node-red-broute
   # そのあと Node-RED を再起動します
   ```

2. メニューから「読み込み」→「サンプル」→ `flows` → `@unlitcube/node-red-broute` → `01-simulator` を選び、読み込みます。タブ「B ルート（シミュレーター）」が増えます。
3. 「デプロイ」を押します。
4. 30 秒ほどで、右のデバッグのタブに架空のメーターの計測値が流れ始めます。
5. `http://<Node-RED のホスト>:1880/wsuha-broute/ui/` を開くと、Web UI で同じアダプタの状態を見られます。

例はほかに 2 本あります。

| 例 | 内容 |
|---|---|
| `01-simulator` | 架空のメーターから値を読みます。デプロイするだけで動きます |
| `02-real-adapter` | 実機のアダプタから値を読みます。ポートと認証情報を入れてからデプロイします |
| `03-alert-and-settings` | つながらない状態の通知（`alert`・`recovered`・Catch）と、inject から送る操作（`settings`・`diag`・`detail`・`read`）を試します |

## 実機をつなぐ

### 1. シリアルポートを開けるようにする

`serialport` はこのノードと一緒に入ります。ビルドできない環境では入らないことがあり、そのときは Web UI に入れ方を出します。

Linux では、Node-RED を動かすユーザーをシリアルポートのグループに入れます。

```bash
sudo usermod -aG dialout <Node-RED を動かすユーザー>
```

実行したら、ログインし直してから Node-RED を起動し直してください。

Docker で動かすときは、デバイスをコンテナへ渡します。

```bash
docker run -d -p 1880:1880 -v node_red_data:/data \
  --device=/dev/ttyUSB0 --group-add dialout nodered/node-red
```

`/dev/ttyUSB*` の番号は、再起動や抜き差しで入れ替わります。入れ替わりを避けるには `/dev/serial/by-id/…` を指定してください。

### 2. ノードを置く

例の `02-real-adapter` を読み込むか、パレットの**ネットワーク**（network）カテゴリにある **B ルート**をフローに置きます（パレットの検索では `broute` か `B ルート` で探せます）。ノードをダブルクリックして、「アダプタ」の鉛筆のアイコンから設定ノードを作ります。

| 項目 | 内容 |
|---|---|
| 接続先 | `Wi-SUN アダプタ（実機）` または `シミュレーター（実機なしで試す）` |
| ポート | `/dev/ttyUSB0`・`COM3` など。候補から選べます |
| 認証 ID | 電力会社から届いた 32 桁の 16 進数（0〜9・A〜F） |
| パスワード | 電力会社から届いた 12 桁の英数字 |
| 取得間隔 | 値を取りに行く間隔（既定 30 秒、15〜3600 秒） |
| 定期的に取りに行く値 | 取得間隔ごとに取りに行く値（既定は瞬時電力 `E7` と瞬時電流 `E8`。1 回の要求に載るので電波の時間はほとんど増えません） |

デプロイすると、自動で接続し、設定した間隔で計測値が出力 1 に流れます。入力を配線しなくても動きます。

### 3. 認証情報の入れ方

入れる場所は 3 つあります。どれか 1 つに入れれば動きます。

- **エディタの設定ノード**: Node-RED が credentials として暗号化して保存します。書き出したフローの JSON には入りません。入れたあとは、認証 ID もパスワードも欄に伏せ字で出し、エディタと管理 API から読み出せません。
- **Web UI の設定タブ**（かフローの入力 `credentials`）: `<userDir>/wsuha-broute/credentials/` に平文で保存します（Linux と macOS ではファイルの権限を 600 にします。Windows では権限を変えません）。userDir を写すときやバックアップするときは、秘密として扱ってください。
- **環境変数**: `WSUHA_BROUTE_ID_<キー>`・`WSUHA_BROUTE_PASSWORD_<キー>`（キーは設定ノードのデバイスキーを大文字にしたもの）か、`WSUHA_BROUTE_ID`・`WSUHA_BROUTE_PASSWORD`。

環境変数がいちばん強く、次に Web UI かエディタのうち後から入れた方が効きます。Web UI で保存したあとにエディタで認証 ID とパスワードの両方を入れてデプロイすると、エディタの値が効きます。エディタの欄が空か片方だけのときは、Web UI で保存した値を使い続けます。どの値も、Web UI・API・ログ・出力には出しません。

フローの入力 `credentials` と `add-adapter` の値を inject や change ノードに書くと、`flows.json` に平文で残ります（書き出したフローと、プロジェクトの git にも入ります）。環境変数か、Web UI かエディタで入れてください。

接続先がシミュレーターの台は、どこにも値が無ければ架空の値で動きます（出どころは「シミュレーターの架空の値」）。ID だけを入れたときと、読めない秘密ファイルがあるときは、入れ間違いに気づけるよう、架空の値を使いません。

> 古い版から移すときだけ、秘密ファイル `wsuha-broute-<キー>.secret.json` も読みます（userDir、Node-RED の作業ディレクトリ、ホームの順に探します。デバイスキーがある台だけです）。新しく入れるときは使わないでください。

### 4. 動力と電力のように 2 契約あるとき

**どの契約につながるかを決めるのは、USB ポートではなく認証情報です。** ポートを差し替えても、同じ認証情報なら同じ契約につながります。

このノードは電波の強さではなく、認証 ID の下 8 桁（PairID）でメーターを選びます。動力と電力のメーターが並んでいる場所では、隣の契約のメーターの方が電波が強いことがよくあるためです。

自分の契約のメーターが見つからないときは、見えている PairID と必要な PairID をログに出します。

```
PAN は 1 件見つかりましたが、この認証情報に対応するメーターがありません
（見えている PairID: AAAABBBB / 必要な PairID: 1234ABCD）
```

この場合は次のどれかです。

- そのメーターが電波の届く範囲に無い
- 認証情報が別の契約のもの
- 認証 ID の転記の誤り

設定ノードの**契約**の欄（`動力` / `電力`）は、認証情報に合わせて設定してください。

## Web UI

`http://<Node-RED のホスト>:1880/wsuha-broute/ui/` で開きます（`httpNodeRoot` を変えているなら、その下）。設定ノードの編集画面の「Web UI で開く」からも開けます。

左にアダプタの一覧（状態・瞬時電力・瞬時電流・電波の強さ・ポートなど。上に全台の合計）、右に選んだアダプタの詳細を出します。幅 900 px 未満のスマートフォンと縦向きのタブレットでは、一覧と詳細を切り替えて使います。

| 右のタブ | できること |
|---|---|
| 状態 | 接続の段階、メーター（PAN・チャネル・電波の強さ・PairID）、再接続の段、換算（係数・単位）、送信積算、カウンター、直近のエラー |
| 計測値 | 直近 24 時間の推移（瞬時電力・電流・電波の強さ）と、すべての値の表。それより前の記録が要るときは、出力 1 をデータベースなどに保存してください |
| 設定 | **アダプタと接続**（名前・契約・接続先・ポート・通信速度・有効・自動で始める・デバイスキー・想定 MAC・スキャンの段階）、**B ルートの認証 ID とパスワード**（入れて保存するだけで、値は表示しません）、**計測**（取得間隔・定期的に取りに行く値・積算の取得間隔・定時積算の取得間隔） |
| 診断 | アダプタの情報とレジスタの読み出し（電波を使いません）、任意の EPC の取得、プロパティマップ |
| ログ | アダプタのログ（レベルの絞り込み・検索・一時停止・.txt で保存） |

操作（今すぐ取得・再接続・停止と開始・自動運転に戻す・セッション終了・送信制限の手動解除）は、右の上にあります。

接続に関わる項目を変えると、その台だけ接続し直します。計測の設定は再接続せずに効き、`<userDir>/wsuha-broute/settings.json` に残ります。

### Web UI でできることは、全部ノードからもできます

Web UI は操作の入口の 1 つです。Web UI・フロー（配線）・エディタのどこから変えても、ほかの 2 つに映ります。

- **エディタ**: 設定ノードの編集画面で、取得間隔・定期的に取りに行く値・積算の取得間隔・定時積算の取得間隔・「有効」を変えられます。Web UI やフローで保存した値（運用設定）が効いている項目は、その値を出します。エディタで値を変えてデプロイすると、その項目の運用設定は外れます。
- **フロー**: B ルートノードの入力で、Web UI と同じ操作ができます（[フローの入出力](#フローの入出力)）。

> エディタの認証の欄は、Web UI かフローで保存した台でも空のままです。認証の欄が空の設定ノードを開いて、何も変えずに［更新］を押すと、Node-RED は変更として扱うので、次のデプロイでその台を作り直します（接続し直します）。変えないときは［中止］で閉じてください。
>
> デプロイの種類を「変更したノード」か「変更したフロー」にすると、B ルートノードだけの再デプロイではメーターとの接続は切れません。「全て」（既定）のデプロイでは設定ノードも作り直すので、つなぎ直すまで 1 分前後止まります。Node-RED 3.1.3 は、設定ノードの編集画面を開いたあとのデプロイでは、値を変えていなくても設定ノードを作り直します。

### 設定の出どころ

設定の項目ごとに、いま効いている値の出どころを出します。強い順に次のとおりです。

1. **一時的な上書き** — 入力の `interval` / `epcs`（デプロイをまたいで残り、`auto` か Node-RED の再起動で消えます）
2. **運用設定** — Web UI か入力の `settings` で保存した値（`settings.json`。再起動しても残ります。変えたのが「Web UI」か「フロー（ノード名）」かも出します）
3. **設定ノード** — エディタで設定した値
4. **既定**

### アダプタの追加

Web UI の一覧の［アダプタを追加］から追加できます。フローの入力 `add-adapter` でも同じです。タブ「B ルート（Web UI で追加）」に設定ノードと B ルートノードが入り、エディタでふつうに編集と配線ができます。Node-RED の内部の仕組みを使うので、3.1 と 4.0・4.1 でだけ使えます（確かめたのは 3.1.3・4.0.9・4.1.2 です）。ほかの版では、エディタで追加する手順を案内します。

Node-RED のプロジェクト機能を使っていると、追加した台は `flows.json` の未コミットの変更として残ります。

`adminAuth` が無いサーバーでは、Node-RED（既定は 1880 番）に届く人は誰でも `flows.json` へ台を追加できます（[エディタを別の方法で閉じているサーバー](#エディタを-adminauth-以外の方法で閉じているサーバー)を除きます）。止めるときは、`settings.js` に `wsuhaBroute: { uiAddAdapter: false }` を書いてください。

### 消した台の値

設定ノードを消しても、認証情報のファイル（`<userDir>/wsuha-broute/credentials/<id>.json`）と、値の入った `settings.json` の `adapters[<id>]` は残ります（無効にしたり、切り取って貼り直したりしたときに値を失わないためです。値の無い記録はデプロイのときに片付けます）。デプロイのたびに、フローに無い id の顔ぶれが変わっていれば warn で知らせます。消すときは、ノードを消す前に Web UI かフローの `credentials-reset` で消してください。ファイルを消すときは、Node-RED を止めてから消してください。

パレットからパッケージを消しても、`<userDir>/wsuha-broute/` は残ります。平文の認証情報が入っているので、要らなければこのディレクトリも消してください。

## フローの入出力

全部の topic と形は [docs/FLOW.md](docs/FLOW.md) にあります。ノードのヘルプ（エディタの右のタブ）にも同じ説明があります。

### 入力

入力を配線しなくても動きます。入力は、そのときだけ動きを変えるものと、Web UI と同じ操作に分かれます。`msg.topic` で指示します（`msg.payload.action` でも指定できます）。

| 何をするか | topic |
|---|---|
| 値を今すぐ取る | `get`・`poll` |
| 持っている最新の値を読む（電波を使いません） | `read` |
| 止める・再開する | `stop`・`terminate`・`start`・`auto` |
| つなぎ直す | `reconnect` |
| 送信制限の扱いを手動で解除する | `clear-radio-block` |
| 取得間隔を一時的に変える | `interval`・`epcs` |
| 運用設定を変える | `settings`・`settings-reset`・`get-settings` |
| 接続の設定と認証情報を変える | `config`・`config-reset`・`get-config`・`credentials`・`credentials-reset` |
| 状態を読む | `status`・`detail`・`trend`・`logs`・`adapters`・`meta`・`serialports` |
| 診断する | `diag`・`command` |
| アダプタを追加する | `add-adapter` |

つながっていないときの `get`・`poll`・`command`・`diag` は、エラーにせずに**預かり**、つながったら来た順に実行します。フローの側で、つながるのを待つ仕組みを作る必要はありません。

### 出力 1 — 計測値

1 回の取得につき 1 通の JSON を出します。

```json
{
  "device": "電力",
  "deviceKey": "usb0",
  "port": "/dev/ttyUSB0",
  "ts": "2026-09-24T15:10:00+09:00",
  "esv": "Get_Res",
  "values": {
    "instantPower": { "value": 409, "unit": "W", "epc": "E7", "name": "瞬時電力計測値", "display": "409 W" }
  },
  "meter": { "panId": "1234", "channel": 33, "channelMHz": 922.5, "mac": "0011223344556677", "ipv6": "FE80:0000:0000:0000:0211:2233:4455:6677", "lqi": 99 },
  "calibration": { "coefficient": 1, "unitFactor": 0.1, "digits": 6 },
  "all": {
    "instantPower": { "value": 409, "unit": "W", "epc": "E7", "name": "瞬時電力計測値", "display": "409 W", "at": "2026-09-24T15:10:00+09:00", "fresh": true },
    "cumulativeForward": { "value": 61552.1, "unit": "kWh", "epc": "E0", "name": "積算電力量計測値(正方向)", "display": "61552.1 kWh", "at": "2026-09-24T15:05:00+09:00", "fresh": false }
  }
}
```

- `values` は、その回に取った値だけです。取得間隔ごとの値と、積算のように間隔の長い値は、別の通で届きます。
- `all` は、これまでに取れた全部の値です。`at` は取った時刻で、その回に取った値は `fresh` が `true` です。どの時点でも全部の項目がそろうので、データベースへ流すときはこちらが便利です。
- `partial` は、メーターが読み出しを断った値があったときだけ `true` で付きます。

瞬時電力は符号付きで、売電のときはマイナスです。積算電力量は、メーターの係数と単位で kWh に換算してあります。

LQI は、応答を受け取ったときの受信の強さ（RSSI）から ROHM の換算式（RSSI ≒ 0.275 × LQI − 104.27）を逆に解いて求めた近似値です。接続の間も応答ごとに変わります。

| EPC | 内容 | 備考 |
|---|---|---|
| `E7` | 瞬時電力計測値 | **符号付き**。売電（逆潮流）のときはマイナス |
| `E8` | 瞬時電流計測値 | R 相 / T 相。単相 2 線式は T 相なし |
| `E0` / `E3` | 積算電力量（買電 / 売電） | 係数と単位で kWh に換算 |
| `EA` / `EB` | 定時積算電力量 | 30 分ごと。日時つき |
| `E2` / `E4` | 積算電力量履歴 | 応答が大きいので単独で取得 |
| `D3` / `E1` / `D7` | 係数 / 単位 / 有効桁数 | 接続した直後に自動で取得 |
| `9F` | Get プロパティマップ | メーターが対応する EPC の一覧 |

### 出力 2 — 状態の変化とイベント

状態の変化（`status`・`phase`・`event`）、入力への返事（入力と同じ topic）、失敗（`error`）、つながらない状態の通知（`alert`・`recovered`）が流れます。payload はどの topic でも、JSON にそのまま変換できるオブジェクトです。json ノードやパーサーを挟まずに使えます。

### つながらない状態が続いたことを知る

このノードは失敗しても自動運転を続けます。通知が無いと、つながらないままになっていることに気づけません。

そこで、連続失敗が設定の回数（既定 3 回）に達したら **1 度だけ**ノードのエラーを出します。**Catch ノードで拾えます。**同時に出力 2 へ `alert` が流れ、主な値（瞬時電力。取得間隔の値に瞬時電力が無ければ取得間隔の値）がまた届いたら `recovered` が流れます（つながっただけでは流しません）。認証や応答が通らないときは、約 5〜7 分で知らせます（認証の試行を 3 回で 1 巡とし、1 巡を連続失敗 1 回に数えます）。定期的に取りに行く値が届かないまま、つなぎ直す回も連続失敗に数えます。

```
[B ルート] ──▶ …
     ▲
[catch] ──▶ [メール / Slack …]
```

B ルートノードの編集画面の詳細設定の「異常の通知」で回数を変えられます。`0` か空なら通知しません。例の `03-alert-and-settings` で、設定ノードの「模擬設定」に `{"fail":{"open":4}}` を入れてデプロイすると試せます（約 30 秒で通知、約 2 分で復旧します）。模擬設定を JSON のオブジェクトとして読めないときは、ログに warn を出して、シミュレーターは既定の動きをします。

> 設定ノードは特定のフローに属さないので、設定ノードのエラーは Catch ノードで拾えません。通知には、フローに置いた B ルートノードの出力と Catch を使ってください。

## セキュリティと settings.js

Web UI と API は、Node-RED の `httpNode`（ダッシュボードの `/ui/` と同じ側）に載ります。このパッケージに独自のログインはありません。

- **読むとき**: 同じネットワークから Node-RED（既定は 1880 番）に届く人は、誰でも Web UI と API の値を読めます。読める人を限るのは、Node-RED の `httpNodeAuth`（ブラウザーの Basic 認証）です。`httpNodeMiddleware` は `http in` ノードにしか掛からないので、Web UI と API は守れません。守るのは `httpNodeAuth` です。
- **変えるとき**: Node-RED に認証（`adminAuth`）があるサーバーでは、Web UI からの変更にはエディタのログインが要ります。`adminAuth` が無いサーバーは、誰でも変更できます。ただし、エディタを別の方法で閉じているサーバー（`httpAdminAuth`・`httpAdminMiddleware`・`httpAdminRoot: false`）では、Web UI からの変更を全部断ります（[下の節](#エディタを-adminauth-以外の方法で閉じているサーバー)）。
- **インターネットへ直接出さないでください。** 外から使うなら、VPN か、認証のあるリバースプロキシの内側に置いてください。

### Node-RED に認証があるサーバー

- 変更するには、同じアドレス（オリジン）で開いたエディタにログインします。Web UI はエディタのログインの情報を使います。Web UI の帯の［Node-RED にログイン］から別のタブでログインして戻ると、変更できるようになります。
- ログインしていなければ 401 `LOGIN_REQUIRED`、権限が足りなければ 403 `FORBIDDEN` です。変更に要る権限は `*`・`write`・`wsuha-broute.write` のどれかで、`read` は読むだけです。`adminAuth.default` で匿名に権限を与えているサーバーでは、その設定どおりに匿名でも変更できます。
- `adminAuth` があるのにエディタが無いサーバー（`httpAdminRoot: false` など）では、ログインできないので、Web UI からの変更を全部断ります。
- `adminAuth` と `httpNodeAuth` の両方があるサーバーでは、Basic 認証とエディタのログインの両方が要ります。ログインが切れたまま保存を押すと、ブラウザーが Basic 認証の入力を求め直すことがあります。入れ直してから、エディタにログインし直してください。
- スクリプトから変更するときは、エディタのトークンを `X-Wsuha-Editor-Token` のヘッダーで送ります（`Authorization` ではありません）。取り方は [docs/API.md](docs/API.md) にあります。
- `wsuha-broute.write` を与えると、Web UI でできる変更の全部（運用設定・接続の設定・認証情報・操作・アダプタの追加）ができます。アダプタの追加は `flows.json` に書き込みますが、`flows.write` の権限は見ません。追加を止めるなら `wsuhaBroute: { uiAddAdapter: false }` を書いてください。
- フローの入力には認証を掛けません。フローは、エディタでデプロイした人が作ったものとして扱います。

### エディタを adminAuth 以外の方法で閉じているサーバー

`httpAdminAuth`・`httpAdminMiddleware` は、`httpNodeRoot` が `httpAdminRoot` の下に無いと、Web UI と API に掛かりません。`httpAdminRoot: false` のサーバーには、エディタがありません。どちらも `adminAuth` が無いと、ログインした人を確かめられないので、Web UI からの変更を全部断ります（401 `LOGIN_REQUIRED`）。読むのは今までどおりです。

- 開くなら、`settings.js` に `httpNodeAuth` か `wsuhaBroute: { allowAnonymousWrites: true }` を書いてください。`allowAnonymousWrites` を書くと、Node-RED に届く人は誰でも変更できます。
- Node-RED を `RED.init` で自分のアプリに埋め込んでいるサーバーには、`httpNodeAuth` と `httpAuth` が掛かりません（掛けるのは `node-red` のコマンドで起動したサーバーだけです）。書いてあっても守りに数えないので、開くのは `allowAnonymousWrites` だけです。読むのと変えるのを限る守りは、ホストのアプリで掛けてください。
- `httpAdminRoot` と `httpNodeRoot` が同じ（既定の `/`）サーバーでは、`httpAdminAuth`・`httpAdminMiddleware` は Web UI と API にも掛かるので、断りません。
- `disableEditor: true` はエディタを出さないだけで管理 API は開いたままなので、この扱いにはなりません（`adminAuth` が無ければ、誰でも変更できます）。守るなら `adminAuth` を書いてください。

### 別のサイトからの読み取りと操作

別のサイトのページからの読み取りと操作は、次のように断ります。

- 書き込みの API は `Content-Type: application/json` が無いと 415、別のサイトの `Origin` からなら 403 にします。応答には CORS のヘッダーを付けません（エディタの CORS が付けたものも外します）。`httpNodeCors` はこの Web UI と API には効きません。
- `Host` が許可リストに無い要求は 403 にします（DNS リバインディングの対策）。IP・`raspberrypi` のような 1 語の名前・`.local`・`.lan` などは既定で通ります。ほかの名前で開くときは、下の `allowedHosts` に追加してください。
- 認証 ID・パスワード・秘密ファイルのパスは、Web UI・API・ログのどこにも出しません（出すのは PairID と出どころの名前だけです）。

### settings.js の wsuhaBroute

`settings.js` に `wsuhaBroute: { … }` を追加すると、Web UI と API の動きを変えられます。どの項目も、フローの入力とエディタには掛かりません。

| 項目 | 既定 | 効くこと |
|---|---|---|
| `ui` | `true` | `false` で Web UI と API を載せません。ノードとフローの入力は動きます |
| `readOnly` | `false` | `true` で Web UI と API からの変更を全部止めます（読むだけになります） |
| `uiConfig` | `true` | `false` で Web UI と API からのアダプタと接続の設定、認証情報の変更、アダプタの追加を止めます。運用設定と操作は使えます |
| `uiAddAdapter` | `true` | `false` で Web UI と API からのアダプタの追加を止めます |
| `allowAnonymousWrites` | `false` | `true` で、エディタを `adminAuth` 以外の方法で閉じているサーバーの変更を開けます。`adminAuth` のあるサーバーの認証は外しません |
| `allowedHosts` | `[]` | `Host` の許可リストに追加する名前（配列か文字列）。`.` で始めると下の名前も通します。ポートは見ません |
| `sse` | `{ maxConnections: 32, maxPerClient: 8 }` | リアルタイム更新の本数の上限（全体・接続元ごと） |

```js
// settings.js の module.exports の中
wsuhaBroute: {
  uiAddAdapter: false,
  allowedHosts: ['nodered.example.com'],
},
```

### リバースプロキシの裏で使うとき

- `Host` を書き換えないでください（nginx なら `proxy_set_header Host $host;`）。公開の名前は `allowedHosts` に追加します。
- TLS を終端するときは、`Host` に加えて `X-Forwarded-Proto` も渡してください（nginx なら `proxy_set_header X-Forwarded-Proto $scheme;`）。渡さないと、Web UI からの保存と操作が 403 `BAD_ORIGIN` になります。
- リアルタイム更新は全体で 32 本、接続元ごとに 8 本までです。リバースプロキシの裏では全員が 1 つの接続元に見えるので、`wsuhaBroute: { sse: { maxPerClient: 32 } }` で増やしてください。上限を超えると 503 `TOO_MANY_STREAMS` で、Web UI は 5 秒ごとの取得に切り替えます。

### http in から入力へつなぐとき

`http in` からつないだ入力には、Web UI の API の保護（Content-Type・Origin・Host・Node-RED の認証・`readOnly`）が掛かりません。別のサイトのフォームからも届きます。つなぐのは読み出しだけにするか、`httpNodeAuth` と `msg.req.headers.origin` の確認を自分で追加してください。

## うまくいかないとき

### メーターが見つからない

次を確かめてください。

- 認証 ID が正しいか
- 電力会社から B ルートの利用開始の連絡が届いているか
- アダプタとメーターの距離

見つかるまで自動で探し続けます。

### メーターは見つかるのに、認証が通らない

ログには `EVENT 24` と出ます。

- 前はつながっていたなら、電波が弱いことが多いです。アダプタの置き場所を確かめてください。
- 初めての接続なら、パスワードと認証 ID が正しいかを確かめてください。

正しいのに通らないときは、前のセッションがメーターに残っていることがあります。メーターは B ルートのセッションを 1 本しか持てません（BP35C0 コマンドマニュアル 3.4 節・3.6 節に基づく）。接続したまま Node-RED を落とすと、次の接続が長時間通らないことがあります。

このノードは閉じる前にセッションを終了し、ポートを開いたときにも前のセッションを終了してから始めます。認証が続けて失敗するときも、止まらずにやり直します。待ち時間を 15 秒から 120 秒まで伸ばしながら同じメーターへ送り直し、30 分続けてもつながらなければメーターを探すところから、それを 3 回続けたらアダプタの初期化からやり直します。15 分たつと、認証情報を確かめるようログで 1 度知らせます。

### 「serialport を読み込めません」と出る

パレットからこのノードを入れ直すか、userDir で `npm install serialport@12` を実行して、Node-RED を再起動してください。

### ポートを開けない

- Linux では、[シリアルポートを開けるようにする](#1-シリアルポートを開けるようにする)を確かめてください。
- ほかの台やフローのシリアルのノードが同じポートを使っていないかを確かめてください。

### 「USB が切断されています」と出る・別のアダプタが見える

`/dev/ttyUSB*` の番号は、USB の列挙の順で決まるので、再起動や抜き差しで変わります。`/dev/serial/by-id/…` を指定してください。

設定の「想定 MAC」にアダプタの MAC アドレス（16 桁の 16 進数）を入れておくと、起動時に照合して、別のアダプタが挿さっていたらエラーで知らせます。

### しばらく送信が止まる

つながらずに再試行を続けている間に送信の積算が上限の約 70% を超えると、ノードは 10 分休みます（[使う前に知っておくこと](#使う前に知っておくこと)）。アダプタが送信の上限に達して送信を止めている間は、電波を使うコマンドを送りません。解除の知らせを取りこぼしたときは、Web UI の「送信制限を手動で解除…」かフローの `clear-radio-block` で解けます。

### 取得間隔を 15 秒より短くできない

1 回の送信は、アダプタの 2 つの応答が返るまで次を出せません（BP35C0 コマンドマニュアル 3.9 節に基づく）。応答を待つ間は次の取得を飛ばすので、短くしても要求は積み上がりません。

### 一部のコマンドを送れない

`WOPT`・`WUART`・`SKSAVE`・`SKERASE` はアダプタの内部 FLASH に書き込み、書き込みの回数には上限（10,000 回）があります。入力の `command` からは実行できません。

ノードは受信の形式が合わないときだけ、`WOPT 01` を 1 回書きます。設定は FLASH に残るので、ふつうは 1 台につき 1 回だけです。

### 長く動かすと値だけ取れなくなる

ファームウェア 1.5.2 rev15 には、電源を入れて約 49 日たつと自動の再認証が止まる既知の不具合があります（BP35C0 コマンドマニュアル 10.7 節に基づく）。このノードはメーターの応答を確かめ、応答が続けて無ければ再接続するので、この状態からも計測に戻ります。

## 更新

**パレットから入れ直しても、動いているコードは入れ替わりません。** Node.js の `require` のキャッシュが残るので、入れ直してデプロイしても、古いコードが動き続けます。パッケージを更新したら、Node-RED を再起動してください（Web UI の帯でも知らせます）。

設定（ポート・認証情報・取得間隔など）の変更は、デプロイするだけで反映されます。再起動は要りません。

## 開発

試験はリポジトリにあります（npm の配布物には入っていません）。リポジトリを取り出して流します。

```bash
npm test     # 実機は要りません（シミュレーターを相手にします）
```

本物の Node-RED に載せる試験と実ブラウザーの試験は、既定では飛ばします。

- `WSUHA_TEST_NODE_RED=<node-red の入ったディレクトリ> npm test` で、本物の Node-RED に載せる試験が流れます。
- `WSUHA_PLAYWRIGHT=<playwright-core のディレクトリ> node --test test/ui/browser.test.mjs` で、実ブラウザーの試験が流れます。

ファイルの構成と、`lib/` を単体で使う方法は [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md) にあります。
